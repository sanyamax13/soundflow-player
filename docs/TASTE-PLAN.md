# Обучение вкусу — план

Alex (TG 18833–18839, 19014): программа смотрит лайки / дизлайки / удаления /
долю прослушанного / пропуски → делает оценку → решает что качать и
регулирует «Поток». Пункт 4 «дороги до продакшена».

Статус: **проект, не начат.** Фундамент: `feature_vector` (2048-d PANNs
CNN14) у 8764 треков, очередь `sync_events`.

Версия 2 (08.09.2026) — после разбора двумя сторонними ИИ (ChatGPT +
Gemini, TG 19016–19020). Оба сошлись на одном; ключевые правки внесены.

---

## Главные принципы (что изменилось после разбора)

1. **Хранить события, не только итоговые оценки.** Оценки — производное,
   пересчитывается. Через полгода захотим «дизлайк весит −2, а не −5» —
   если сохранены только оценки, всё потеряно.
2. **Никакой тяжёлой ML-модели.** 8800 треков + готовые эмбеддинги — это
   размер для *понятного* ranking'а, а не для нейросети, которую потом не
   отладить. Каждый коэффициент должен объясняться: «почему трек получил
   0.87 → +0.42 близость к долгому вкусу, +0.21 к недавнему, +0.14 артист…».
3. **Explicit ≫ implicit.** Лайк/дизлайк/удаление — несоизмеримо весомее
   пропуска и доли прослушивания.
4. **Не один «центр вкуса», а несколько.** У человека параллельно
   synthwave, метал, эмбиент, джаз. Среднее по ним — «каша», не похожая ни
   на что. Кластеризуем любимые треки, держим отдельные центроиды.
5. **Отделять типы негатива** (см. §2). «Не та версия» ≠ «не нравится».
6. **Вся математика на компе** (программа-сервер). Телефон остаётся плеером.

## 1. Сигналы (что собираем с телефона)

Четыре независимых типа, не смешивать:

| Тип | События | Смысл |
|---|---|---|
| `taste_positive` | лайк, повтор трека, дослушал 90–100%, дослушал 75% | нравится |
| `taste_negative` | дизлайк, удаление с причиной «не нравится» | не нравится (пессимизируем вектор и окрестность) |
| `context_negative` | пропуск (ранний / обычный) | «не сейчас» — мягкий, накопительный; НЕ «никогда» |
| `catalog_negative` | удаление «не та версия» / «дубликат» / «плохой файл» | к вкусу ≈ 0, это сигнал качеству |

Веса (концептуально, подбираются экспериментально):

```
лайк               +5
повтор подряд      +3
дослушал 100%      +1.5
дослушал ~75%      +0.8
обычный пропуск    -0.3
ранний пропуск (<20с / <15%)  -0.7
дизлайк            -5
удалил «не нравится»          -5
удалил «не та версия»        ~0 (в taste), +сигнал качеству
```

**Надо добавить на телефоне** (мелкая правка Flutter, нужен тест на устройстве):
- в событие `skip` класть `{position_ms, duration_ms}` — сейчас позиции нет;
- новое событие `complete` — песня закончилась сама;
- у `delete` уже есть `reason` (не нравится / не та версия) — использовать.

Уверенность: один пропуск — шум; три пропуска одной песни — сигнал.
Повторяющиеся события весомее разовых.

## 2. Затухание — разное для разных сигналов

`effective_weight = original_weight × exp(−возраст / τ)`, но τ своё:

```
лайк / дизлайк      → очень медленное (месяцы), НЕ до нуля («золотой фонд»)
повтор              → среднее
доля прослушивания  → быстрое
пропуск             → быстрое
сессионный сигнал   → очень быстрое (часы)
```

Иначе: неделю слушал техно → система решила «это его вкус» → через полгода
он на эмбиенте, а техно всё ещё «основная личность».

## 3. Профиль вкуса — три слоя

```
score = 0.60·long_term + 0.25·recent + 0.15·session
```

- **long_term** — что нравится годами.
- **recent** — что стало интересно в последние недели.
- **session** — что хочется прямо сейчас (тёмное / медленное / инструментал).
  Вес session динамически растёт после нескольких подряд согласованных
  действий (3 ритмичных пропустил + медленный дослушал → очередь сразу
  перестраивается под медленное).

Каждый слой — не один центроид, а **набор кластеров** (k-means, 3–5 центров
на слой), появляются автоматически из `taste_positive`-треков.
Кандидата меряем косинусом к **ближайшему** кластеру, не к среднему.
Векторы перед этим нормализовать (PCA/whitening по желанию — для 8800
локально не проблема).

## 4. Оценка кандидата (что качать)

```
rank(track) =
    w1·similarity_to_long_term
  + w2·similarity_to_recent
  + w3·artist_affinity          (отдельный сигнал, НЕ часть track preference)
  + w4·recent_release_bonus     (свежий релиз любимого артиста — бонус, не гарантия)
  + w5·session_continuity
  − w6·repetition_penalty
```

**Каналы кандидатов с квотами** (пример на 100):

```
35  похожие на текущий вкус (по эмбеддингу)
25  новые релизы любимых артистов
15  похожие артисты (Яндекс)
10  забытые жемчужины (в каталоге, давно не играл, когда-то нравилось)
10  разведка (exploration — см. §5)
 5  случайное
```

Каждого кандидата — через **правила RULES.md §2** (качество, не обрезок,
язык, не в блок-листе, не дизлайкнут).

## 5. Разведка (не переобучиться на узкий вкус)

Не «магически крутить веса», а прямо заложить бюджет:

```
80–90%  эксплуатация (по вкусу)
10–20%  контролируемая разведка
```

Разведка = кандидат с чуть меньшей похожестью, но рядом с одним из
кластеров, у незнакомого артиста / необычного жанра. Лайкнул — система
получила очень ценные данные (мини-contextual-bandit).

«Температура» (Gemini): чем больше подряд ранних пропусков — тем шире
радиус поиска, система «нащупывает» настроение.

## 6. Разнообразие — считать отдельно (MMR-переранжирование)

Не `sort by score DESC` (получится 20 треков одного артиста), а после
оценки:

```
final_score = preference_score − λ · similarity_to_already_selected
```

Топ-20 остаётся вкусным, но не двадцать вариаций одного.

## 7. Радио («Поток») ≠ профиль вкуса

Разные задачи: «что человеку в принципе нравится» и «что поставить
следующим треком». Второе зависит от предыдущих треков, темпа, энергетики,
повторов, усталости от артиста, текущего настроения.

→ У радио-очереди **свой ranking поверх базового профиля**:
- поднимать треки из кластеров с высоким score;
- опускать/пропускать артистов со `score_artist < 0`;
- не ставить подряд недавно пропущенное;
- не больше 2 треков одного артиста подряд;
- сессионный слой с повышенным весом;
- 10–15% на трек «далеко от текущих центроидов» (антипузырь).
Полный запрет — только дизлайк/удаление (это уже blocklist).

Автоподбор новых треков идёт в **окно ручной синхронизации** отдельным
списком «Предлагаю по вкусу» с галочками. Не качаем молча.

## 8. Данные

```
feedback_event
--------------
track_id, artist, event_type, timestamp, context, value, reason
```

`event_type`: like, unlike, dislike, replay, finish, skip_early, skip_normal,
delete_not_my_taste, delete_bad_version, delete_dup.

`taste_track`, `taste_artist` — **derived state**, пересчитываются из событий.
`taste_cluster` — центроиды по слоям (long/recent/session), пересчёт по
расписанию.

1. **Телефон: сигналы.** `skip` с позицией, событие `complete`, читать

   **Не сделано** — уйдёт в APK после проверки v30.
2. **Сервер: события + оценка.** `feedback_event`, пересчёт после

   (коммит `e37e7ac`): таблица `feedback_event` (храним события, не оценки),
   `deriveFeedback` (like +5 / finish +1.5 / skip_early −0.7 / skip_normal
   −0.3 / dislike·«не нравится» −5 / «не та версия»·дубль 0),
   `recordFeedback` в транзакции `SaveSync`, `TasteArtists` / `TasteTracks`
   / `TasteTotals`, `RebuildFeedback` (разовая пересборка из истории,
   идемпотентна), `GET /api/taste` + `POST /api/taste/rebuild`. Тесты
   `TestDeriveFeedback`, `TestTasteRoundTrip`. Работает уже сейчас на
   today-телефоне через skip_normal/like/delete; skip_early/finish — после
   этапа 1. `taste_track`/`taste_artist` как отдельные derived-таблицы пока
   не заводили — считаем суммой на чтении (8800 треков, мгновенно).
3. **Сервер: кластеры по звуку.** k-means по слоям, `similarity` кандидата.
   **СДЕЛАНО в коде** (коммит `3da0fa7`): `kmeans.go` (spherical k-means
   без пакетов), `taste_cluster` (слой 'all', задел под long/recent/session),
   `RecomputeTasteClusters` (k = 3/4/5), `tasteAffinity`,
   `ScoreTracksByTaste` (основа канала «похожие на вкус»), `TasteClusters`
   (центры + треки-примеры). `POST /api/taste/cluster`. Тесты
   `TestKmeansCosineSeparates`, `TestRecomputeTasteClustersAndScore`.
   Слои и декей — с этапом, где появится время-взвешивание.
4. **Автоподбор.** Каналы+квоты → rank → MMR → список в окно синхронизации.
   **ЯДРО СДЕЛАНО в коде** (коммит `6384e8c`): `SuggestDownloads(deviceID, n)`
   — каналы «по вкусу» / «забытое» (любимый артист, не играл >30 дней) /
   «на пробу» (близость 0.45–0.78) / «случайное», квоты 45/20/20/15 (§4
   минус два внешних канала — их доля перераспределена), MMR-разнообразие
   (λ=0.35). `GET /api/devices/{id}/suggest?n=30`. Тесты
   `TestSuggestDownloads`, `TestSuggestDownloadsEmptyWhenAllOnPhone`.
   **Осталось:** секция «Предлагаю по вкусу» с галочками в окне ручной
   синхронизации (нужен макет), каналы Яндекса («новые релизы любимых
   артистов», «похожие артисты»), слои long/recent/session, тюнинг весов
   по живой картине вкуса. Частота/объём — §11.
5. **Радио.** Свой ranking-слой в `OrderBySimilarity` + сессия + разведка.
   **Не начато.**
6. **Окно.** Вкладка «Вкус»: топ-исполнители, что предлагает, ползунок
   «сколько нового качать», объяснение оценки трека. **Срез 1 СДЕЛАН**
   (коммит `b492885`): сводка + «Любимые/Не заходят» по исполнителям и
   трекам + «Направления вкуса по звуку» (центры + примеры) + кнопка
   «Пересобрать». Ползунок и объяснение оценки — с этапом 4.

Этапы 2, 3, 6(срез 1) — фундамент, уже польза (видно вкус). 1 (телефон) +
4–5 — «умное». Автоподбор — после переезда на комп и ручной синхронизации.

## 10. Как проверять (один пользователь — не 8800 наблюдений)

**Временной holdout**, не случайный split:
```
обучение янв–июн → тест июль → обучение янв–июл → тест авг → …
```
Метрики: попал ли liked/replay высоко; сколько dislike в топ-K; сколько
новых артистов реально принято; разнообразие; новизна; концентрация по
артистам; сколько рекомендаций пришлось пропустить. Отдельно —
known-artist vs unknown-artist (cold-start).
