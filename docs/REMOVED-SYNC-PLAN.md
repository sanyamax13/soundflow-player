## Что уже есть (проверено по коду 19.09.2026)

Телефон: `DownloadsRepo.delete` (`apps/mobile/lib/data/downloads_repo.dart`) —
стирает файл и кладёт в очередь событие `delete` с причиной; очередь уходит на
сервер при связи (`SyncRepo`/`AutoSync`). (До APK v62, 19.09.2026, он ещё писал
строку в локальный журнал `removed_tracks` для экрана «Профиль → Убранные»;
экран и запись убраны, таблица в старых базах осталась неиспользуемой.)

Сервер: `handleDeleteEvents` (`apps/server/internal/api/api.go`), на каждое
НОВОЕ принятое событие `delete`:
1. метка `blocked` в `legacy_marks` по ключу «исполнитель + название»
   (нормализованному) — не попадает в каталог, повторный импорт и повторное
   скачивание (проверяется в `yandex_wave.go`, `acquire`);
2. файл стирается насовсем (`pathmap.DeleteForever`, без корзины — Alex
   06.09.2026);
3. в лог сервера «убран из плеера» с размером;
4. причины `bad_quality`/`wrong_version` — иначе: строка трека стирается, метка
   `blocked` НЕ ставится, фоном ищется замена (`deleteAndReacquire`).

Вкус: `apps/server/internal/localdb/taste.go` — `delete` с обычной причиной =
сигнал `delete_not_my_taste`, вес −5; `bad_quality`/`wrong_version` = 0 (сигнал
качеству, не вкусу); `dup` = 0.

Список «больше не качать» был виден в приложении («Сервер → Больше не качать»,
`GET /v1/admin/blocklist`, «Убрать» у строки); с APK v62 экрана на телефоне нет,
ручка на сервере осталась.

Обрабатываются только события, принятые впервые (`accepted`), чтобы не дёргать
файл при повторном синке. Значит, всё, что сервер принял ДО появления обработчика
(или пока обработчик падал), повторно не разбирается.

## Предложение ассистента (не реализовано)

Не строить новый механизм, а сделать разовый «догон» с защитой:

1. Телефон присылает серверу полный список `removed_tracks`.
2. Сервер сравнивает и показывает ОТЧЁТ (сухой прогон, ничего не стирая): сколько
   убрано на телефоне, но лежит на ПК; сколько уже в блок-листе; сколько не узнал.
3. После явного «да» Alex файлы уходят в карантин-папку на 7 дней, затем стираются.
   Одиночные удаления работают как сейчас.
4. Потолок: если под удаление больше N% библиотеки — остановиться и спросить.
5. Вкус: сотни удалений дадут сотни минусов (−5) — показать эффект заранее, при
   необходимости ограничить вес/затухание.
6. «Не качать похожее» — отдельный следующий этап (фильтр по звуковым отпечаткам).

Правила безопасности (глобальный CLAUDE.md): перед удалением — бэкап (здесь его
роль играет карантин), сухой прогон с точным списком, явное подтверждение Alex.
Развёртывание сервера на fg возможно только когда он доступен.

## Найдено при проверке (19.09.2026): лишняя метка при «плохом качестве»

(`internal/localdb` через `internal/litestore`). Её `localdb.SaveSync`
(`internal/localdb/phone.go`, появилось в коммите bfa0767, шаг 4 «один exe»)
при приёме события `delete` ставил метку `blocked` ЛЮБОМУ удалению, включая
причины `bad_quality` и `wrong_version`. Для этих двух причин Alex решил
05.09.2026 (PROGRESS, этап 22): метку НЕ ставить, иначе поиск замены сам себя
отклоняет — `acquire` при метке отвечает «в старом плеере удалён или скрыт»

переезде.

Следствие (по коду): все удаления с телефона с причиной «плохое качество» /

На живом сервере не проверено (fg недоступен с brain).

причин; тест `internal/localdb/phone_delete_test.go` (падал на двух из четырёх

## Ответы сторонних ИИ (19.09.2026, принёс Alex)

19935–19937). Совпадают в главном; расходятся в числах.

Что совпало:
1. **Идемпотентность.** У каждого события — стабильный uuid, повтор не должен
   снова ставить −5, стирать файл, дублировать метку. Для догона — тоже
   «применить максимум один раз».
2. **Карантин 7 дней мало** — оба советуют 14 (второй — 14–30 или «пока не
   кончится место»). Цена лишних дней — только диск.
3. **Не сверять файлы по «исполнитель+название» для физического удаления.**
   Такой ключ хорош для мягкого «не предлагай», плохой для стирания:
   студийная/живая/ремастер — разные записи. Неоднозначные совпадения — в отчёт,
   не в стирание.
4. **Гонка:** трек убран на телефоне давно из-за плохого качества, сервер за это
   время скачал замену — догон по названию сотрёт новую версию. Нужны id/дата.
5. **Вкус:** исторические удаления не должны давать −5 каждое; слабее (около
   −1…−2), потолок на артиста (≈−10) и на всю партию (≈−100), пометка
   «историческое»; затухание по времени; `bad_quality`/`wrong_version` вкус не
   учит (у нас уже 0 в `taste.go`).
6. **Похожесть по звуку не делать жёстким запретом.** Близость векторов = «звучит
   похоже», не «тебе это не нравится». Сначала только понижение приоритета в
   подборе; запрет — лишь для «той же записи» (отпечаток + длительность +
   название), после проверки порогов на своих данных.
7. **Отчёт до применения** по категориям: точное совпадение / вероятное / несколько
   / не найдено; по причинам; сколько файлов в карантин, сколько сигналов вкуса,
   сколько поисков замены.

Расходятся: потолок. Первый: подтверждение при >100 или 2%, жёсткий стоп при
>300 или 5%. Второй: min(5%, 50 треков), всё больше 50 за сеанс — только после
ручного разбора. Оба считают, что разовый догон всегда требует подтверждения.

## Что беру, что нет (мнение ассистента, ждёт решений Alex)

Беру:
- **Сверка по id трека, а не по названию.** В журнале телефона
  (`removed_tracks`, `apps/mobile/lib/data/db.dart`) первичный ключ `id` —
  серверный id трека, плюс `removed_at` и `reason`. Это снимает главный риск из
  пунктов 3–4: замена, скачанная после удаления, получила бы новый id и
  под удаление не попадёт. Название — только для вероятных совпадений в отчёте.
- **Карантин 14 дней**, стирание после срока. Цена — диск.
- **Отчёт (сухой прогон) по категориям выше**, стирание только у точных.
- **Потолок:** разовый догон всегда после явного «да» на конкретный список; для
  обычной синхронизации — стоп, если за один сеанс просят стереть больше 50
  файлов (ждёт ручного разбора).
- **Вкус для догона:** около −1,5 вместо −5, потолок −10 на артиста и −100 на
  партию, пометка «историческое». Затухание по времени — отдельно, позже.
- **Идемпотентность:** у событий uuid уже есть (`sync_events.event_uuid`,
  `ON CONFLICT DO NOTHING`); для догона — отдельный журнал партии (что
  планировалось, что применено, что восстановлено).
- **Похожее по звуку:** сначала только понижение приоритета, не запрет.

Не беру (слишком тяжело для личной библиотеки на ~8800 треков): полное
разделение «композиция / запись / предпочтение», MusicBrainz, Chromaprint.
Сверка по id уже даёт нужную точность; отпечатки — позже, если понадобится
«та же запись под другим id».

Это новая функция с развилками — по правилу проекта сперва обсудить с Alex
(что показывать, где смотреть отчёт, как называть, срок карантина), потом
делать. Пока ждём два числа.

## Что в интернете (для контекста решения)

- Удаления передают отдельной записью-«надгробием», а не выводом «чего-то нет —
  значит стереть»; сначала мягкое удаление, стирание байтов позже; потолок
  «сколько можно удалить за раз» и правило «действовать, только если несколько
  сверок подряд согласны»: https://github.com/artifact-keeper/artifact-keeper/issues/3987
- Блок-лист «больше не качать» (Lidarr) хранится, пока сам не уберёшь; блокирует
  тот же самый релиз: https://wiki.servarr.com/lidarr/activity
